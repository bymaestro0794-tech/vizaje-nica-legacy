# M5.4.3 — Legacy referral analytics

This implementation follows `vz-partners/docs/m5.4-referral-analytics-integration.md` and the checked-in Partners routes and schemas. It is additive and disabled by default.

## Runtime flow

- `FrontEndController` consumes `vp_attribution` before rendering a storefront page, exchanges it server-to-server once, saves only the signed opaque context in the active PHP session for no longer than its supplied expiry (at most seven days), removes the one-time token from the URL, and redirects to the same relative URL. Exchange is gated by marketing consent. Reading and cart mutations do not refresh the attribution expiry.
- `Ajax::cart_add()` queues `add_to_cart` only after the cart write succeeds, with analytics consent and the server-side context. It sends the accepted quantity and internal `products.id`; no browser price or customer data is sent.
- `Cart::checkout()` adds the opaque context, its exact expiry, a millisecond-resolution order-creation timestamp, and an incomplete-snapshot marker to the inserted order row when the follow-up patch exists. It marks the snapshot complete and queues `order.created` only after every `orders_products` row was saved. Legacy emits no order event if the order-creation timestamp is at or after the attribution expiry. Later status events remain tied to the valid order snapshot and are not invalidated merely because the seven-day window has since passed. The existing checkout transaction boundaries are unchanged.
- Paynet's successful callback records `paid` only after it has set `pay_success=1`. Admin status changes enqueue their corresponding event after the saved status is reloaded. `finished` is a status update, never proof of payment. A `progress` event is suppressed after successful payment to avoid status regression.
- A CLI-only reconciliation worker rebuilds missing order events from complete order snapshots. A verified `paid` state is reconstructed once from `pay_success` and its saved timestamp; the status snapshot does not create a duplicate `paid` event. It serializes delivery per order: a later status is held until the earlier event is delivered. Temporary transport failures retry with exponential backoff; permanent API errors are marked failed with a sanitized code.

## Contract details

- Exchange: `POST /v1/internal/referral-analytics/attribution/exchange`, exact request `{ "handoffToken": "..." }`; response must contain exactly `attributionContext` and `expiresAt`.
- Cart event: `POST /v1/internal/referral-analytics/events`.
- Order event: `POST /v1/internal/referral-analytics/order-events`; payloads contain no personal information and use `orders.id` in the namespaced order key.
- Each event uses a stable event ID for retry, a new timestamp/nonce/signature for each HTTP attempt, and the contract's exact HMAC canonical string. The client verifies TLS, does not follow redirects, limits response bytes, and accepts only the documented event acknowledgment.
- Order state mapping: `new` → `order.created`; `progress` / `paid` / `finished` → `order.updated`; `confirmed` → `order.confirmed`; Legacy `canceled` → contract `cancelled` / `order.cancelled`.

## Local setup (manual only)

The independent Legacy flag is `PARTNERS_REFERRAL_ANALYTICS_ENABLED=false` by default. Provision these only in the dev PHP process environment after coordinating the same dev key with Partners:

```text
PARTNERS_REFERRAL_ANALYTICS_ENABLED=false
PARTNERS_REFERRAL_ANALYTICS_API_URL=https://<partners-dev-api-origin>
LEGACY_ANALYTICS_HMAC_KEYS=[{"keyId":"legacy-analytics-to-partners-dev-<key-id>","secret":"<base64url-secret-at-least-32-bytes>","active":true}]
```

Do not enable this on Legacy dev until a non-production Partners API origin and its separate dev key are confirmed. Do not point the dev site at the production API. Do not place key material in Git, a public `.env`, browser code, logs, or the webroot. No key was generated or configured by this change. Use separate keys for dev and production.

Review the additive patch at `database/patches/2026-11-12-create-partners-referral-analytics-outbox.sql`, take a database backup, and apply it manually to a non-production database. The patch has **not** been applied by this implementation. It adds five order context/status/payment/reconciliation columns and one outbox table; the reconciliation-state field tracks status/payment snapshots without relying on second-resolution timestamps.

The separate follow-up patch `database/patches/2026-11-16-add-partners-referral-context-expiry.sql` adds two nullable `DATETIME(3)` order snapshot columns. Review it and apply manually after backup, only after the earlier outbox patch. Until both columns exist, Legacy deliberately declines referral order snapshots/events while leaving checkout unaffected. Do not rerun either patch if its columns are already present.

## Seven-day attribution lifetime

- Partners supplies the absolute click expiry (`click time + 604800 seconds`). Legacy preserves its millisecond precision in the existing server-side `ci_session` and in the order snapshot. A repeated page view or cart action never extends it; a newly exchanged valid referral context replaces the previous session context.
- Checkout snapshots the expiry and the current millisecond-resolution time immediately before inserting the order. An order created exactly at expiry is ineligible. No click or cart event creates an order/commission by itself.
- Legacy's native file session is configured for 210 days, with a persistent `ci_session` cookie and explicit PHP lifetime settings. The cPanel `.htaccess` contains 30-day values, but application startup attempts to override them. Browser cookie retention and host-level session-file cleanup are external runtime behavior; local code cannot guarantee the host will preserve the session files for seven days. This design uses the existing strictly necessary shop session only and creates no additional visitor identifier or cookie.
- The current marketing-consent gate remains in force. If marketing consent is absent or withdrawn, Legacy does not use the referral context. No fingerprinting, IP matching, or browser storage is used. Whether this purpose can rely on the existing session without marketing consent requires a separate legal basis review; this change does not bypass consent.
- Partners currently validates order events against the context's expiry at event-ingestion time. Therefore delayed delivery of a valid `order.created`, and status updates after day seven, may be rejected there even though Legacy captured a valid in-window order. Partners must preserve eligibility from the accepted order snapshot and allow its later status lifecycle without extending click attribution. This remains an external integration blocker; this Legacy change does not alter commission or payment rules.

After the patch and dev environment are configured, run the sender from the project root:

```text
php index.php partners_referral_analytics_worker run
```

Schedule it with the hosting's CLI cron only after the dev smoke tests pass. The worker rejects web requests. Keep the feature flag false until the matching API routes and HMAC key are provisioned.

## Verification limits

The local PHP 7.4 regression scripts exercise exact expiry comparisons, context replacement, consent-gated session use, order snapshots, and order-event eligibility with an injected clock and fake database. Database-dependent checkout, callback, outbox, and end-to-end exchange tests require both additive patches and a reachable non-production Partners API. Neither a migration nor a remote API request is performed by this change.
