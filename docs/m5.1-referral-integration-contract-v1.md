# Vizaje Partners ↔ Vizaje-Nica Legacy Referral Integration Contract

**Contract:** M5.1, version `1.0.0`
**Status:** Proposed; specification only
**Date:** 2026-11-04
**Systems:** Vizaje Partners (Hono/Bun/PostgreSQL) and Vizaje-Nica Legacy (CodeIgniter 3/PHP 7.4/MySQL)

This document defines the service boundary for resolving a creator-supplied destination and carrying a validated referral click into Legacy. It does not authorize an order, calculate commission, or implement any part of the contract.

## 1. Confirmed identity and URL rules

> **Legacy route correction, 2026-11-07:** brands and categories use the same catalog route shape. Canonical routes are `/{locale}/{localized-catalog-page-uri}/{entity-uri}`: RU normally `/ru/katalog/{uri}` and RO normally `/ro/catalog/{uri}`. Brand `uri` is shared across locales; the catalog page URI and locale prefix are localized. The Legacy resolver must classify the final segment through catalog records, following `Catalog::category()` precedence: a visible category is selected before a brand with the same URI. If a visible category and brand collide, the URL resolves as a category and a request with `expectedType: "brand"` must fail with `TYPE_MISMATCH`. Partners must synchronize this correction before relying on brand resolution.

- A referral link represents one Legacy entity and one Partners referral code, not one code per language.
- Supported entity types are `homepage`, `product`, `category`, and `brand`.
- Product identity is the local `products.id`. `products.GUID` is the external 1C identity and is returned as supplemental reconciliation data; it is not the URL key and is not required to resolve the product in the same Legacy database.
- `products.category_id` identifies the product's primary category. Legacy's existing route/canonical URL generation remains responsible for selecting the current category route and producing the product URL.
- Product `uriRU` and `uriRO` are independent. A final URL segment that looks numeric is still a URI segment and must never be treated as `products.id` or SKU.
- Category and brand identity uses each Legacy record's stable local primary key, represented on the wire as a decimal string. Slugs are never entity identifiers.
- A brand has one URI shared by both locales. Legacy returns separate localized RU and RO brand URLs using that same URI; Partners does not synthesize or translate either URL.
- Category and brand pages share `/{locale}/{catalog-page-uri}/{slug}`. Segment count alone cannot distinguish them. Legacy first looks up a visible category using the localized URI; only when none matches does it look up a visible brand using the shared `brands.uri`. Hidden categories do not shadow brands because the public category lookup excludes hidden rows. Multiple visible matches of the same entity type are rejected as ambiguous.
- Legacy is the only authority for current canonical URLs. Stored paths are snapshots/fallback candidates, never the source of entity identity.
- All JSON timestamps are RFC 3339 UTC (`Z`). All URL values are HTTPS in production. Local development origins are excluded from this production contract.

Example product URLs for the same Legacy product:

```text
RU https://vizaje-nica.com/ru/katalog/paletki/39897
RO https://vizaje-nica.com/ro/catalog/paletki/39897
```

The resolver must match each URL through Legacy routing/catalog data and return the same local `products.id` for both. It must not infer that ID from `39897`, and must not derive either URL from the other by replacing path segments.

## 2. Service authentication

All new internal endpoints use HTTPS and directional HMAC-SHA256 authentication. The existing M4 `x-service-token` validation endpoint remains available unchanged during this contract's rollout; it is not the authentication method for the new endpoints.

### Request headers

```http
Content-Type: application/json
X-VP-Key-Id: partners-to-legacy-2026-01
X-VP-Timestamp: 1793810000
X-VP-Nonce: <22-character-base64url-value>
X-VP-Signature: <64-character-lowercase-hex>
```

The direction-specific key IDs are provisioned independently, for example `partners-to-legacy-2026-01` and `legacy-to-partners-2026-01`. Secrets contain at least 32 random bytes. Each application keeps a key ring so the old and new key IDs can overlap during rotation. A key ID selects a secret and is included in the signature. Every key ID maps to a stable service principal (`vizaje-partners` or `vizaje-legacy`); authorization and idempotent retry ownership use that principal, never the rotating key ID. `/internal/v1/referrals/resolve-target` authorizes only `vizaje-partners`; `/internal/v1/referrals/tickets/redeem` authorizes only `vizaje-legacy`. Valid HMAC from another principal is still unauthorized for that endpoint.

### Canonical signing string

The signature is lowercase hex of `HMAC-SHA256(secret, UTF8(canonicalString))`. The canonical string has exactly seven lines, LF (`0x0A`) separators, and no trailing newline:

```text
VP-HMAC-SHA256-V1
{key-id}
{UPPERCASE_METHOD}
{canonical-path-and-query}
{unix-timestamp-seconds}
{nonce}
{lowercase-hex-SHA256-of-raw-body-bytes}
```

Rules:

1. The method is uppercase (`POST`). The path is the exact origin-relative path sent on the wire. Internal calls in this version have no query string; any query string is rejected. Do not include scheme, host, fragment, or default port.
2. The timestamp is a base-10 Unix timestamp in whole seconds with no sign or leading zeroes, except `0`.
3. The nonce is 16 cryptographically random bytes encoded as unpadded base64url (22 characters). Generate a fresh nonce and timestamp for every network attempt, including retries.
4. Hash the exact UTF-8 bytes of the JSON body as transmitted, before parsing. Do not reserialize before verifying. Bodies are limited to 16 KiB, contain no duplicate JSON object keys, and use `application/json; charset=utf-8`.
5. Compare signatures in constant time. Reject duplicate authentication headers. TLS certificate and hostname verification are mandatory; HMAC authenticates the calling service, while TLS authenticates the endpoint and protects the response.

Each receiver allows at most 60 seconds of timestamp skew. It atomically inserts `(key_id, nonce)` into a replay table with a unique constraint before processing the request. A repeated nonce returns `409 AUTH_NONCE_REPLAY`, even if its signature is valid. Keep nonce rows for at least 10 minutes. HMAC, timestamp, and nonce failures return `401 SERVICE_AUTH_INVALID`, `401 SERVICE_TIMESTAMP_INVALID`, and `409 AUTH_NONCE_REPLAY` respectively. Do not log signatures, secrets, tickets, ticket query strings, cookies, or request bodies containing tickets.

`entity.id` is the local Legacy primary key, serialized as a string. For products it is exactly `products.id`; `sourceGuid` is supplemental. `targets.ru` and `targets.ro` are independently generated by Legacy. For a brand, the slug is shared, but each target uses the current localized catalog page URI and locale prefix (for example `/ru/katalog/{uri}` and `/ro/catalog/{uri}`). A category/brand URI collision resolves to the visible category because that is the route order in Legacy; a brand is not successfully resolved through that colliding URL. `fallback.path` is an exact Legacy-generated relative path for the requested locale when available; otherwise it is the available locale's canonical path. If neither locale is available, the resolver fails with `LOCALE_UNAVAILABLE` or `ENTITY_UNAVAILABLE` rather than inventing a path.

Legacy must resolve product URLs using its existing product route and canonical URL builder, joining the product with its primary `products.category_id` and that category's localized URI. It then matches the full route URI back to the product record. It must not parse the final path segment as an ID. For categories and brands, it resolves each localized/shared URI to the stable local record before returning its ID.

## 4. Referral link storage and language behavior

New M5.1 links store the stable entity identity and use `link_type` plus `legacy_entity_id`; localized URLs are snapshots only. Each referral code has one `preferred_locale` and one `fallback_path`, but the entity is language-independent. On a short-link request, an optional `?lang=ru` or `?lang=ro` is accepted as a display-language preference only. Any other query parameter is rejected. If absent, Partners uses the link's `preferred_locale`.

Partners passes the selected locale in the ticket. Legacy resolves the current route for that locale from the entity ID at claim time. When the user later switches RU/RO, Legacy resolves the same entity ID using the independent locale URI. It never changes `/ru/katalog/` to `/ro/catalog/` (or vice versa) by string replacement. If the requested-language translation is unavailable but the entity is available in the other language, Legacy redirects to that independently generated alternate URL. It records the actual displayed locale. If no language target is available, it returns an unavailable page and does not set a new attribution cookie.

An entity that has moved keeps the same referral code: Legacy returns the current canonical URL by ID. Stale stored slugs are not used as the primary destination. The stored fallback path is considered only after Legacy confirms that it still resolves to the same entity; otherwise it is ignored.

## 5. Public click, one-time ticket issuance, and Legacy handoff

### 5.1 Ticket issuance at Partners

The existing public short-link path remains:

```http
GET /r/{code}
GET /r/{code}?lang=ru
GET /r/{code}?lang=ro
```

For an entity-resolved M5.1 link, Partners verifies in one database transaction that:

- the code exists;
- the referral link is active and unexpired;
- the owning partner is a creator with active/approved access;
- the entity identity was resolved and stored.

It creates a random UUID `click_id`, a random 32-byte opaque ticket encoded as unpadded base64url (43 characters), and stores only `SHA-256(ticket)` in the database. It stores an immutable redemption snapshot containing the link, partner and creator identifiers, entity identity, selected locale, fallback, issue time, and ticket ID. The raw ticket is never logged or persisted. Partners redirects with `303 See Other` to a fixed configured Legacy URL, for example:

```text
https://vizaje-nica.com/referral/claim?t={opaque-ticket}
```

The destination host/path for the claim route comes only from server configuration; it is never accepted from the browser. The ticket is the only value in the query. No creator ID, partner ID, entity ID, or destination URL is accepted from an unsigned browser parameter. Partners sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on its redirect; Legacy applies those headers on claim responses too, redacts the query from access/application logs, and immediately redirects away from the ticket URL after success.

The ticket is valid for **5 minutes from issuance**. An unredeemed ticket may be exchanged once. Partners validates link/creator status and link expiry again at exchange time; a link revoked, expired, or whose owner lost active creator access after issuance is not redeemable.

Each new `GET /r/{code}` is one public click attempt and creates its own `click_id`/ticket; only a ticket redeemed by Legacy can update Legacy attribution. An unredeemed ticket has no attribution effect and expires after five minutes. A retry of the internal redemption call is idempotent as specified below. Reopening or reloading `/r/{code}` is a new click attempt because a browser navigation does not carry an idempotency key.

Before exchanging a ticket, Legacy establishes a stable first-party visitor identity so a lost browser response cannot make a retry look like a different visitor:

1. `GET /referral/claim?t=...` validates an existing signed `vp_visitor` cookie. If absent/invalid, it generates a random 32-byte visitor ID, sets a signed `vp_visitor` cookie with a 15-minute bootstrap expiry, then returns `303` to the fixed `GET /referral/claim/continue?t=...` route. It does not contact Partners or consume the ticket on this bootstrap response.
2. `/referral/claim/continue` requires the valid bootstrap or existing visitor cookie before exchanging the ticket. If the cookie was not stored by the browser, it returns a neutral cookie-required/retry page rather than looping or consuming the ticket.
3. If the browser already has a valid attribution cookie but no `vp_visitor`, Legacy may recover the visitor ID only after verifying the attribution cookie MAC and its unexpired current/ledger record, then reissue `vp_visitor` with the same expiry.
4. After a valid click is persisted, Legacy sets/refreshes both cookies to the click's fixed `issuedAt + 7 days` expiry. If the Partners response or final browser response is lost, the visitor cookie remains stable and Legacy retries the same ticket.

The claim routes accept only `t` (and no user-controlled destination); the ticket is redacted from logs. A bootstrap redirect preserves `t` only between the two fixed Legacy routes and is also `no-store`/`no-referrer`.

Exact browser endpoints and outcomes:

```http
GET https://vizaje-nica.com/referral/claim?t={ticket}
GET https://vizaje-nica.com/referral/claim/continue?t={ticket}
```

The first route returns `303` to `/referral/claim/continue?t=...` and sets the bootstrap cookie when needed. The continue route returns `303` to the Legacy-generated canonical entity URL only after ticket redemption, entity availability checks, and durable attribution commit succeed; it sets both seven-day cookies on that response. Missing/malformed ticket returns a neutral `400 CLAIM_TICKET_INVALID` page. If the browser does not retain the bootstrap cookie, return `409 VISITOR_COOKIE_REQUIRED` with a retry instruction and do not call Partners. If `click_id` already exists for a different visitor hash, return a neutral `409 CLICK_VISITOR_MISMATCH` page and do not change either visitor's attribution. Invalid/unknown, expired, or inactive tickets render neutral `404`/`410` pages and never expose creator/link data. These browser pages are not internal JSON APIs.

Bootstrap response header when creating a visitor cookie:

```http
Set-Cookie: vp_visitor=<signed-value>; Max-Age=900; Expires=<now+900-seconds>; Path=/; Secure; HttpOnly; SameSite=Lax
```

### 5.3 Single-use, replay, and idempotency

Ticket redemption is atomic in Partners. A unique ticket hash and row lock/CAS ensure only one initial transition from `issued` to a terminal state (`redeemed` or `rejected`) wins. If the first response is lost, Legacy retries the same raw ticket with a newly signed HTTP request (fresh timestamp and nonce). For a redeemed ticket, Partners returns the saved immutable response fields and values for the same authenticated Legacy service principal for **10 minutes after first redemption**. It does not create another click, re-read mutable link state, or extend any expiry. This is an idempotent transport retry of a consumed ticket, not a second redemption.

If the first eligibility check finds a revoked/expired link or inactive creator, Partners atomically stores `state=rejected`, `rejection_code=REFERRAL_INACTIVE`, `rejected_at`, `processed_by_service_id`, and a 10-minute `retry_until` before returning `410 REFERRAL_INACTIVE`. A retry by the same service principal within the retry window returns the same error without rechecking mutable state; another principal receives `409 TICKET_PROCESSED_BY_OTHER_SERVICE`. Transient failures do not move the ticket to a terminal state.

An already-processed ticket sent with a different service principal is rejected. After the 10-minute retry window, neither the success snapshot nor the stored terminal error is returned. Replayed HTTP requests with an old nonce are rejected by the HMAC nonce table; a retry must use a new nonce. A ticket that has not been redeemed within five minutes is rejected. Ticket state, response snapshot or rejection result, and retry window are committed in one Partners transaction before the response is written.

Legacy also writes attribution idempotently using `click_id` as its unique click identity. The ledger binds that click to exactly one `visitor_id_hash`; reusing a click from another visitor is rejected and cannot replace either visitor's current attribution. If its claim request is retried after Legacy committed the attribution but before the browser received the final `303`/cookies, the preflight visitor cookie and same `click_id` allow Legacy to reconstruct the same visitor association and signed attribution cookie. The retry never advances the click time or seven-day expiry.

| 401 | `SERVICE_TIMESTAMP_INVALID` | Timestamp outside ±60 seconds. |
| 409 | `AUTH_NONCE_REPLAY` | Nonce already seen for this key ID. |
| 404 | `TICKET_NOT_FOUND` | Ticket hash unknown; response does not distinguish any link/creator data. |
| 409 | `TICKET_PROCESSED_BY_OTHER_SERVICE` | Ticket is redeemed or rejected and retry caller is not the original service principal. |
| 410 | `TICKET_EXPIRED` | Unredeemed ticket is past its 5-minute expiry. |
| 410 | `TICKET_RETRY_WINDOW_EXPIRED` | Idempotent retry window has elapsed. |
| 410 | `REFERRAL_INACTIVE` | Link is revoked/expired, creator is no longer active, or ticket's link is otherwise ineligible at first redemption. |
| 422 | `TICKET_ENTITY_INVALID` | Stored ticket entity snapshot is malformed or unsupported. |
| 429 | `RATE_LIMITED` | Per-service/per-ticket limit reached; includes integer `Retry-After` seconds. |
| 503 | `PARTNERS_TEMPORARILY_UNAVAILABLE` | Transient service/database failure. |

Rate limits: resolver 60 requests/minute per authenticated service; ticket redemption 30 requests/minute per service plus 10 requests/minute per ticket hash. Enforce in addition to network-level service allowlisting. A rate-limit rejection does not consume an unredeemed ticket.

## 7. Seven-day attribution and Legacy first-party cookie

### Valid click definition

A click becomes valid only when all these conditions pass: Partners issued a ticket while the link and creator were eligible; Partners accepted its first exchange while they remained eligible; Legacy successfully resolved the entity to an available canonical destination. `issuedAt` from the authenticated Partners redemption snapshot is the click time. It must be within the ticket's five-minute lifetime and not more than 60 seconds in the future relative to Legacy's clock. `accepted_at` is the UTC time Legacy commits the click ledger and current-attribution row in one transaction.

On a valid click, Legacy stores `expires_at = issued_at + 604800 seconds`. A later distinct valid click for the same browser replaces the current attribution and starts a new seven-day window. A retry with the same `click_id` does not change `issued_at`, `expires_at`, or the current row. A click that cannot resolve to an available entity, or is rejected by Partners, does not overwrite a prior valid attribution or set a new cookie. Revoking a link after a valid click does not retroactively erase that click's seven-day attribution.

### Persistent Legacy records

Legacy owns attribution persistence independently from the PHP session:

- `referral_attributions` is an append-only click ledger keyed uniquely by `click_id`. It stores `visitor_id_hash`, `referral_link_id`, `creator_id`, `entity_type`, `entity_id`, optional product `source_guid`, `requested_locale`, `resolved_locale`, `issued_at`, `accepted_at`, `expires_at`, and `created_at`. The unique click binding prevents the same bearer ticket from attributing the click to multiple visitors.
- `referral_attribution_current` has one row per `visitor_id_hash` and stores the current `click_id`, `issued_at`, `expires_at`, and `updated_at`. It is updated atomically only when an incoming valid click is newer than the current `issued_at`. This prevents a delayed response for an older click from replacing a newer click.
- `visitor_id_hash` is SHA-256 of the decoded 32 random visitor-ID bytes (not the base64url text). Legacy never stores the raw visitor cookie value.
- Legacy may retain expired click-ledger rows under its normal retention policy; order/commission linking is a later milestone.

The browser carries two signed first-party cookies. `vp_visitor` holds the stable visitor ID used to associate later valid clicks. Its value is:

```text
v1.{visitorId}.{expiresUnix}.{mac}
```

For bootstrap, its expiry is 15 minutes from issuance. After a valid referral click, its expiry is set to the click's absolute seven-day expiry. `visitorId` is 32 random bytes encoded as unpadded base64url. Its MAC is lowercase hex HMAC-SHA256 with the Legacy cookie signing key over the following exact newline-delimited UTF-8 string (no trailing newline):

```text
VP-VISITOR-COOKIE-V1
{visitorId}
{expiresUnix}
vizaje-nica.com
```

`vp_attribution` carries the click attribution:

```text
v1.{visitorId}.{clickId}.{expiresUnix}.{mac}
```

`visitorId` is the same 32-byte ID as in `vp_visitor`, encoded as unpadded base64url. `clickId` is a UUID. `mac` is lowercase hex HMAC-SHA256 using the Legacy cookie signing key over this exact newline-delimited UTF-8 string, with no trailing newline:

```text
VP-ATTRIBUTION-COOKIE-V1
{visitorId}
{clickId}
{expiresUnix}
vizaje-nica.com
```

Legacy verifies both MACs with constant-time comparison, requires matching visitor IDs when both cookies exist, verifies the attribution cookie against matching current/ledger rows and expiry, and ignores invalid/expired cookies. Set both cookies' `Expires` to the exact absolute click expiry after a valid click. Set `Max-Age` to the nonnegative integer number of seconds remaining until that expiry, calculated at response time (floor fractional seconds so the cookie cannot outlive the server-side seven-day window):

```http
Set-Cookie: vp_visitor=<value>; Max-Age=<remaining-seconds>; Expires=<issuedAt+7d>; Path=/; Secure; HttpOnly; SameSite=Lax
Set-Cookie: vp_attribution=<value>; Max-Age=<remaining-seconds>; Expires=<issuedAt+7d>; Path=/; Secure; HttpOnly; SameSite=Lax
```

Do not set `Domain` when RU/RO use the confirmed shared canonical host `vizaje-nica.com`; this keeps the cookie host-only. If production uses locale subdomains, that deployment must explicitly confirm the registrable-domain cookie scope and update this contract before rollout. `Cache-Control: no-store` and `Referrer-Policy: no-referrer` are set on claim responses. The ticket is removed from the address bar by the `303` to the current canonical URL.

When an older valid ticket arrives after a newer valid click for the same `visitorId`, Legacy preserves the newer `referral_attribution_current` row and returns cookies for that current row, not the older click. When the current click is the same `clickId`, the same cookie values and absolute expiry are returned; `Max-Age` is recalculated from that unchanged expiry, so a retry never renews the seven-day window. If that expiry has passed, Legacy must not reissue valid-looking attribution cookies. Language switching, catalog filters, product browsing, and checkout retain the cookies because they are host-only and use `Path=/`; server-side attribution is read from Legacy's table, not from PHP session lifetime.

### Orders are explicitly out of scope

M5.1 stores click attribution only. Legacy checkout currently does not have a transaction spanning the order and all order lines. Therefore this contract does not write an attribution FK into a partially created order, create commission rows, or promise order-level exactly-once attribution. A later milestone must add an order-completion/idempotency boundary or a reconciliation process before using this data financially.

## 8. Timeouts, retries, and outage behavior

| Call | Connect timeout | Per-attempt total | Attempts | Retry delay |
| --- | ---: | ---: | ---: | --- |
| Partners → Legacy resolver | 500 ms | 2 s | 2 total | 150 ms |
| Legacy → Partners ticket redeem | 500 ms | 2 s | 3 total | 150 ms, then 400 ms |

The total caller deadline is 5 seconds for resolution and 7 seconds for redemption. Each attempt signs the same logical request body with a fresh timestamp/nonce. Retry only network/connect timeouts, HTTP `408`, `429` (respect `Retry-After`, capped at 1 second and within the deadline), `502`, `503`, and `504`. Do not retry other `4xx` responses. Never retry with a new ticket to recover a lost redemption response; retry the same ticket.

- **Legacy unavailable during link creation:** Partners does not create a new entity-resolved link. Return retryable `503 LEGACY_TEMPORARILY_UNAVAILABLE`; preserve the user's form values.
- **Legacy unavailable after ticket redirect:** show a branded temporary error/retry page. Retry the same claim URL/ticket while eligible. Do not silently redirect to an unverified/stale path and do not set a cookie.
- **Partners unavailable during redemption:** Legacy shows temporary unavailable with a retry action; do not set a cookie or send a raw destination. The ticket remains redeemable until expiry, or the already-redeemed response remains retrievable during its retry window.
- **Partner link revoked/expired or creator inactive at first redemption:** Partners returns `410 REFERRAL_INACTIVE`; Legacy does not set/replace attribution and shows a neutral unavailable page.
- **Entity unpublished/deleted or not found:** Legacy does not set/replace attribution. Return a friendly `404`/`410` page; do not redirect to a stale stored slug.
- **Requested locale missing but entity available in alternate locale:** Legacy chooses the alternate URL returned by its own current resolver, records `resolved_locale`, and sets attribution only after redirect target selection succeeds.
- **Partner's non-redeemed ticket expires:** Legacy displays a restart link to the original short URL only if that path can be recovered from its server-side claim state; otherwise show a neutral expired-link page. Do not issue a new click implicitly.
- **Legacy database unavailable:** no durable valid attribution can be confirmed. Do not set the cookie; show retryable error.

All endpoint and web request logs must exclude `t` from `/referral/claim`, the raw ticket, cookie value, and HMAC signature. Query-string logging for that route is disabled/redacted at proxy, web-server, APM, and application layers.

## 9. M4 compatibility

M4 remains additive and backward compatible:

1. Keep the public `/r/{code}` route, existing 10-character opaque code, and M4 internal `POST /v1/internal/referral-links/validate` contract unchanged during migration.
2. Preserve existing `target_protocol`, `target_host`, `target_path`, `link_type`, status, expiry, code, label, and timestamps. Do not rewrite or regenerate codes.
3. Add entity metadata as nullable fields. New link creation requires successful Legacy resolution. Existing M4 links may be backfilled by submitting their stored target to the resolver.
4. A successfully resolved existing link starts using the ticket flow with the same code. Its canonical destination then comes from Legacy by entity ID.
5. An unresolved/ambiguous legacy row remains on its previous allowlisted M4 redirect behavior, and is marked in operational reports as **not M5.1 attributed** until resolved. Do not guess an entity from a slug/numeric path segment. Do not turn a transient M5.1 outage for a resolved link into an untracked direct redirect.
6. Revoked/expired link behavior remains unchanged. Existing link status and expiration are rechecked before ticket issuance and first ticket redemption.

The existing M4 validation endpoint still returns its existing response for existing consumers. The new ticket endpoint is a separate, service-authenticated contract and does not repurpose M4's `valid: true/false` response.

## 11. Safe migration and rollout order

All steps below are future rollout steps; none are performed now.

1. Record counts of active, revoked, expired, and path-only M4 links; take normal database backups and verify restore procedures. Confirm production canonical hosts and that RU/RO share the cookie host.
2. Provision independent directional HMAC keys, Legacy cookie signing key, clock synchronization, rate limits, request-log redaction, TLS, DNS, and monitoring. Do not reuse `REFERRAL_SERVICE_TOKEN` as an HMAC key.
3. Apply an additive Legacy migration for nonce replay protection, click ledger, and current-attribution table. Do not alter checkout/order tables.
4. Deploy Legacy HMAC middleware and resolver endpoint first. Keep existing site routes and M4 behavior unchanged. Verify resolver read-only results for both locales and all entity types.
5. Apply an additive Partners migration for nullable link identity fields, tickets, and nonce replay table. Keep all old M4 columns and rows intact.
6. Deploy Partners ticket issuance/redeem and resolver client behind a disabled feature flag. Verify cross-service authentication and failure behavior in staging.
7. Run an idempotent **dry-run** backfill report against M4 links. Resolve only unambiguous destinations. Review unresolved and ambiguous counts and sample URLs before writing entity fields; never infer from the last segment.
8. Backfill resolved rows in bounded batches, preserving code and old target columns. Repeat safely using `resolved_at`/identity match; verify counts and sample RU/RO paths.
9. Enable entity resolution for new links, then enable ticket redirects only for entity-resolved links. Keep path-only M4 behavior for unresolved rows. Monitor resolver failures, ticket age/replay/rate-limit counts, claim failures, and cookie persistence.
10. Retain the M4 validation endpoint until all known consumers are migrated and explicitly retired in a later change. Rollback disables the feature flag; it does not drop new fields/tables or rewrite old rows.

## 12. Required RU/RO and security test cases

### Resolver

1. The supplied RU product URL and RO product URL resolve to the same `product.id`, with independently returned RU/RO URLs and the same supplemental `sourceGuid`.
2. A product with differing `uriRU`/`uriRO` returns each exact Legacy canonical path; no string substitution is used.
3. A product whose final URL segment is numeric but differs from `products.id` resolves by route/URI to the correct product ID.
4. Product URL generation follows `products.category_id` and the category's localized route when the primary category changes.
5. A category with different RU/RO slugs resolves to one stable category ID and two independent targets.
6. A shared-URI brand resolves from the real catalog route to one stable brand ID and two independently generated targets, such as `/ru/katalog/{uri}` and `/ro/catalog/{uri}`.
7. A category/brand slug collision follows Legacy route precedence: the visible category resolves as a category, and the same URL with `expectedType: "brand"` returns `TYPE_MISMATCH`.
8. Localized homepage request returns `/ru/` or `/ro/` as requested; locale-less root uses `requestedLocale`.
9. Wrong expected type, locale mismatch, unsupported host, query/fragment, credentials, encoded separators, unknown URI, ambiguous route, and unpublished entity return their specified errors.
10. A stale stored slug for an existing ID is never returned as the current canonical path.

### Ticket, attribution, and retries

10. An active RU or RO link issues one opaque ticket and redirects only to the fixed Legacy claim origin.
11. Changing `?lang=ru`/`?lang=ro` selects a language but does not change code, creator, link, or entity IDs; arbitrary query params are rejected.
12. Successful ticket exchange returns typed identity; Legacy resolves current URL itself, then stores a click and signed cookie.
13. Concurrent first redemption attempts create one snapshot/click; a same-principal retry returns the original immutable response values and does not create a click, even if the caller has rotated to another valid key ID.
14. Lost redeem response followed by retry with fresh HMAC nonce returns the original result; repeating the old nonce is rejected.
15. Different service identity cannot replay a ticket; expired unredeemed ticket and expired retry window return the specified errors.
16. Revoke/expire link or deactivate creator between issuance and first redemption; exchange is rejected and existing attribution is untouched.
17. Lost browser redirect after Legacy committed is retried with the same click ID/cookie/expiry and does not renew the seven-day period.
18. A second distinct valid click updates the visitor current row and starts a new seven-day window; an older delayed claim does not overwrite it.
19. RU↔RO switching, filtering, product navigation, and checkout requests on the canonical host retain the same valid cookie/current click.
20. Missing locale translation falls back only to Legacy's current independently resolved alternate URL; missing/unavailable entity sets no new cookie.
21. Invalid/expired/tampered cookie is ignored; cookie signature is compared in constant time; raw ticket/cookie/signature never appears in logs.
22. Legacy unavailable, Partners unavailable, DB unavailable, 429, 5xx, timeout, and retry exhaustion show a recoverable neutral error without an untracked M5.1 redirect or a new cookie.
23. Existing M4 path-only links retain their old safe redirect; resolved/backfilled M4 links keep their same code and enter the ticket flow; ambiguous M4 paths remain un-attributed and are not guessed.
